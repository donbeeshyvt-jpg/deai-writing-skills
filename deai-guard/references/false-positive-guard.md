# 誤判防護：豁免規則與各文類特殊處理

這份檔案是 deai-guard 的信任核心。偵測 AI 味的規則本身會冤枉好文章，這裡列出什麼情況該降級、什麼情況根本不該判、什麼情況只能標「可能」而不能標「確診」。碰到判斷邊界，優先讀這裡，不要拿詞彙表硬套。

一個總原則先講清楚：命中詞彙不等於命中問題。同一個詞在某個文類是套話，在另一個文類是這行的正常用語。判 AI 味要看「內容有沒有空泛」，詞彙只是線索，不是證據。

## 目錄

- 一、各文類豁免規則
- 二、短文本特殊處理
- 三、非母語與繁簡轉換處理
- 四、詞彙層過度判斷的警告

- 六、什麼時候不要判
- 七、誠實邊界

## 一、各文類豁免規則

下面每一條都是「看到這個信號，不扣分」的白名單。逐條照做，命中白名單就在報告的「可能誤判」欄註明，不列入嚴重度排序。

### 1. SEO 標題與 H 標籤：重複關鍵字不扣分

搜尋引擎要靠關鍵字對應查詢，標題和小標重複同一個詞是刻意的排版需求，不是同義詞輪轉失敗，也不是節奏過勻。

| 情況 | 判或不判 |
|---|---|
| title、H1、H2 重複出現主關鍵字 | 不判，這是 SEO 結構 |
| meta description 出現關鍵字 | 不判 |
| 正文段落內同一個抽象詞每句都出現、且不給具體 | 這才判，屬空泛 |

before（別把這個當同義詞輪轉扣分）：

```
H1：台北搬家推薦
H2：台北搬家費用怎麼算
H2：台北搬家注意事項
```

這是正常 SEO 佈局，三個 H2 重複「台北搬家」是對的。不要為了「自然」把它改成「都會區遷居」「搬遷成本試算」，那會直接傷害排名。

判準：重複的是標題層（title／H）就放行；重複的是正文論述層、且該段沒有具體內容才算問題。

### 2. 技術文件：術語鎖定

術語、API 名稱、參數名、設定鍵、指令、路徑、版本號一律鎖定，不改、不換同義詞、不「自然化」。技術文件的價值就在術語精確，改了就是製造錯誤。

| 這些看起來像 AI 味，但在技術文件正常 | 為什麼放行 |
|---|---|
| 反覆出現同一個術語（例：每段都寫 middleware） | 換詞會讓讀者對不上，術語必須一致 |
| 制式步驟語（首先、接著、最後） | 步驟文件本來就要標順序 |
| 被動語態（該值會被覆寫） | 描述系統行為的標準寫法 |
| 「透過設定 X 來達成 Y」 | 這是操作說明的直述，不是翻譯腔 |

技術文件只清「開場暖場」和「結尾升華」兩處，正文與術語全鎖。範例：

- 可清：開頭「在當今快速發展的雲端時代，容器化已成為不可或缺的技術」→ 刪掉暖場，直接寫「這份文件說明怎麼用 Docker 打包這個服務」。
- 不可碰：正文「將 `NODE_ENV` 設為 `production` 後，快取層會啟用」→ 一個字都不動。

### 3. 法規、條款、報價：原文不改

法律條款、合約用語、報價單、規格表的字句有法律或商業效力，換句話說可能改變意思。這類內容一律鎖定，只在明顯的行銷包裝段落（不是條款本身）才判 AI 味。

- 條款編號、條文序號、金額、幣別、單位、有效期：全鎖。
- 「本公司保留最終解釋權」這類制式法律句：不判，這是慣用語不是套話。
- 報價項目名稱、規格參數：全鎖，不換同義詞。

唯一可判的，是包在條款外面的推銷文字（例如報價單開頭那段「我們致力於為您打造卓越的解決方案」），這屬文案，按文案規則處理。

### 4. 學術摘要：背景鋪陳是文類需求

學術摘要的固定結構就是背景、方法、結果、結論。開頭鋪陳研究背景、用被動語態、句子偏長、引用格式規整，這些是學術寫作的規範，不是 AI 味。大幅降級，幾乎不判。

| 學術摘要常見特徵 | 一般文章會判，學術摘要不判 |
|---|---|
| 開頭鋪陳領域重要性 | 摘要的 introduction 就是這樣寫 |
| 被動語態密集 | 學術客觀性要求 |
| 長句、子句多 | 精確表達複雜關係的需要 |
| 無第一人稱、無個人取捨 | 學術文體本來就抑制個人聲音 |

學術摘要唯一還能提的，是內容矛盾（方法和結論對不上）或明顯拼接痕跡（前後主題不連貫）。詞彙層、節奏層、聲音缺失層全部降到最低權重。

### 5. 公文與 email：制式結尾正常

公文有稱謂、事由、正文、制式結尾的固定格式。「敬請  查照」「耑此奉達」「順頌  時祺」「此致」這類結尾語是公文規範，不是 AI 升華收尾。email 的「若有任何問題歡迎隨時聯繫」也屬禮貌慣用語。

- 稱謂、署名、機關全銜、文號、日期：全鎖。
- 制式起頭與結尾語：不判。
- 引用的法規條號、公文用語：不判。

公文只清「明顯機械的開場套話」，而且要非常保守。多數情況公文不需要動。

## 二、短文本特殊處理

文本越短，可判的信號越少。硬判短文只會誤傷。按字數分級，越短越不判。這一段呼應父技能第一段步驟 2。

| 字數 | 處理方式 |
|---|---|
| 500 字以上 | 完整流程，五維度評分 |
| 300 到 500 字 | 只出風險等級加最嚴重 3 條命中加修正方向，不做五維度評分 |
| 300 字以下 | 只看「邏輯有無矛盾」和「用詞有無明顯拼接痕跡」，其餘不判 |

300 字以下的具體限制：

- 不算節奏勻稱度。短文本來就沒有足夠句子去看句長變化，兩三句等長不代表機械。
- 不算聲音缺失度。短文可能就是沒空間放個人立場，不能因此扣分。
- 不算模板度中的「結構公式」。三句話談不上結構。
- 能看的只有兩件事：內容有沒有自相矛盾，用詞有沒有像拼接自不同來源的痕跡（例如前半句口語後半句突然公關腔，且明顯不連）。

報告開頭要明講：「短文本信號不足，只做輕量判斷，以下不代表全面評估。」不要給短文一個看起來很精確的五維度分數，那是假精確。

## 三、非母語與繁簡轉換處理

作者不是中文母語者，或文章是翻譯、機翻潤飾、簡轉繁而來，會帶天然的翻譯腔和用詞生硬。這些是來源特性，不是 AI 生成特徵。硬拿「透過…來實現」判 AI 味會冤枉真人作者。這一段呼應父技能第一段步驟 4。

執行順序：

1. **先問來源。** 開判之前問一句：「這是你自己用中文寫的，還是翻譯、改寫、或簡轉繁過來的？」答案決定後面的權重。
2. **確認是非母語或翻譯來源後，降翻譯腔權重。** 詞彙層和翻譯腔層的權重調到最低，不拿「透過…來實現」「進行一個…的動作」「使得」這類直接判 AI。
3. **重點放內容密度和邏輯。** 看的是有沒有具體的事、主張有沒有出處、前後有沒有矛盾，而不是句子順不順。

繁簡轉換要特別留意的機械痕跡（這些屬轉換問題，不是 AI 味，標記但不列 AI 命中）：

- 詞彙沒在地化：軟件（軟體）、信息（資訊）、質量（品質）、視頻（影片）。這是簡轉繁沒調詞，屬校對問題。
- 一詞多轉的錯字：「著」與「著」、「余」與「餘」、「里」與「裡」轉錯。
- 標點半形殘留：簡體來源常帶半形逗號句號。這要轉全形，但屬格式問題不是 AI 味。

把這些跟 AI 味分開列。報告裡寫成「繁簡轉換待校」而不是「AI 味命中」，兩者的處理路徑不同：前者是校對，後者才走去 AI 味流程。

## 四、詞彙層過度判斷的警告

最容易誤判的就是詞彙層。有一批詞在商業文案、行銷、品牌溝通裡本來就是高頻用語，不是 AI 專屬。看到就扣分，誤判率偏高。

高頻但常被誤判的詞（在商業文案語境下多半正常）：

| 詞 | 為什麼商業文案本來就高頻 |
|---|---|
| 透過 | 「透過這個功能你可以…」是產品說明的常見句式 |
| 體現 | 「這個設計體現了品牌精神」是行銷慣用語 |
| 賦能 | 科技與 B2B 文案的常駐詞，指給能力 |
| 打造 | 「打造專屬體驗」在文案裡幾乎是標配 |
| 提升、優化 | 產品與行銷語境的日常詞 |

判準不在詞，在詞後面有沒有東西。同一個「賦能」，接得出具體對象就正常，接不出就空泛。

before / after 對照：

- 命中（空泛，該判）：「我們的平台賦能企業，體現價值，打造未來。」三個抽象詞連排，找不到誰被賦能、賦了什麼能、打造什麼。
- 不命中（具體，放行）：「這個 API 讓小型團隊不必自建金流，兩天就能接上刷卡。」意思相近，但講得出對象和結果。

重要：這裡不給精確誤判百分比。詞彙層誤判率偏高是操作經驗的質性描述，不是實測統計。報告裡也照這個規矩，只寫「此類詞在商業文案高頻，誤判率偏高」，不要寫「準確率 60 到 70%」「誤判超過三成」這種沒有出處的數字。本技能自身守誠實邊界，不自產假數字。

## 五、段落等長陷阱

「每段長度差不多」常被當成節奏過勻的證據。但 Markdown 的列表、表格、步驟編號會自動讓每一項看起來等長，這是排版產生的，不是作者在機械化寫作。單看等長就判，會誤傷所有用列表的文章。

會自動等長、不該單獨扣分的排版：

- 項目符號列表（每個 bullet 一行，天然接近等長）。
- 編號步驟（1. 2. 3. 每步一句）。
- 表格欄位（格子強制對齊）。
- FAQ 的問答對（問題句型相近）。

確診節奏過勻要同時滿足兩個條件：

1. 段落或句子等長。
2. 而且內容空泛（每段都在講重要性、不給具體、抽象名詞堆疊）。

只有第 1 條沒有第 2 條，不判。範例對照：

- 不判：一份操作教學用了六個等長的編號步驟，每步都有具體指令。等長來自步驟格式，內容紮實。
- 判：一段沒有列表的正文，連續五句幾乎同長，每句都是「X 至關重要」「Y 不可或缺」這種宣告，沒有一句給例子。等長加空泛，才確診。

寫報告時，如果等長來自列表或表格，要在「可能誤判」欄註明「等長來自 Markdown 排版，非機械寫作」。

## 六、什麼時候不要判

這是一張快速決策表。碰到左欄情況，右欄就是動作。這張表的作用是在動手前攔下誤判。

| 情況 | 動作 |
|---|---|
| 文本 300 字以下 | 只看邏輯矛盾與拼接痕跡，其餘不判 |
| 命中詞彙但內容具體、有來源、有判斷 | 降級，不扣分 |
| 重複的是 SEO 標題或 H 標籤 | 不判，這是搜尋結構 |
| 是術語、API 名、參數、指令、路徑、版本號 | 全鎖，不判不改 |
| 是法規條款、合約、報價、規格 | 原文不動，只看外層行銷段 |
| 是學術摘要的背景鋪陳、被動語態 | 大幅降級，這是文類需求 |
| 是公文或 email 的制式結尾語 | 不判，這是格式慣用語 |
| 作者是非母語或內容是翻譯、簡轉繁 | 先問來源，降翻譯腔權重 |
| 詞是透過／體現／賦能／打造且商業文案語境 | 看後面有沒有具體，沒有才判 |
| 等長來自列表、表格、編號步驟 | 不判，除非同時內容空泛 |
| 使用者明講「這段不要動」 | 直接鎖定，繞開 |
| 引用、引號內的原話 | 不改，這是別人說的 |
| 單一訊號命中、沒有同段聚集 | 不算數，要多訊號聚集才記 |

決策表的用法：先過這張表，過得了才進評分。過不了的直接放行或標「可能誤判」，不進嚴重度排序。

## 七、誠實邊界

這一段把這個技能能保證什麼、不能保證什麼講到底。判斷權最後在使用者手上，這裡界定的是工具的能力範圍，不是話術。

**能保證的：**

- 能指出文字裡呈現了哪幾個 AI 味特徵，並附上命中的具體句子。
- 能標出每一條命中「在什麼情況下其實正常」，也就是可能誤判的理由。
- 確認閘門之前不改任何一個字。
- 不動事實、數字、術語、引用、命令、專有名詞。
- 改寫時不新增原文沒有的事實與來源，查不到就標 [待查] 或 [待補]。

**不能保證的：**

- 不能保證判定等於「這是 AI 寫的」。呈現 AI 味特徵的可能是真人，刻意工整的真人文章會命中規則。
- 不能給 AI 生成機率的百分比。分數只是命中嚴重度的排序工具，不是生成概率。
- 不能替代使用者對自己文章意圖的判斷。某段是不是刻意工整，作者比工具清楚。
- 不能保證抓全。低命中不代表一定是真人寫的。

**什麼情況降級（信號不足時主動退讓）：**

- 文本過短（300 字以下降到只看邏輯與拼接）。
- 技術文件、公文、法規、學術摘要（按各文類豁免降級）。
- 非母語或翻譯、簡轉繁來源（降翻譯腔與詞彙層權重）。
- SEO 文與文案（保留結構，只看正文空泛與節奏）。
- 命中集中在會自動等長的排版（列表、表格、步驟）。

**永遠不說的話：**

- 不說「這一定是 AI 寫的」。只說「這幾處呈現 N 個 AI 味特徵」。
- 不說「AI 生成機率 X%」。
- 不用沒有出處的精確數字去描述誤判率或準確率。要提就用質性描述，或明講這是經驗值、非實測。

報告結尾固定附一句，提醒使用者判斷權在他手上：「以上是特徵判斷，不是 AI 生成的確認。是否修改由你決定。」
