## 一、內容物理學

寫作先過物理，再談文采。讀者的眼睛和注意力有它自己的規律，寫的人擋不住，只能順。

### 2 秒摺疊之上定律

手機螢幕第一屏能看到的區塊叫「摺疊之上」。讀者滑進來的頭 2 秒只掃這一塊，決定要不要往下。這 2 秒裡看不到答案，人就走了。

落地做法：

- 第一屏（標題加第一段）必須有直答句。不要把答案藏在第三段。
- 第一段不做背景鋪陳，不做名詞解釋，不預告「這篇會談什麼」。那些都塞不進 2 秒。
- 標題本身要能被獨立讀懂，不靠內文補完。

反例和正解：

| 寫法 | 第一屏給的東西 | 讀者反應 |
|---|---|---|
| 「在資訊爆炸的年代，我們每天面對大量選擇⋯」 | 一句誰都知道的廢話 | 滑走 |
| 「三款筆記軟體我都用滿一個月，只有一款留下來。」 | 一個具體結論加懸念 | 往下讀 |

### F 型閱讀

眼球掃網頁走 F 型：先橫掃第一行，往下一點再橫掃一次，然後沿左緣垂直往下跳著看。這代表兩件事。

一是重點靠左。放在一行最左邊的字被讀到的機會最高，放最右邊的常被跳過。所以每個小節、每個段落，把最重要的字放在開頭，不要用「首先」「關於這一點」這種佔位詞把左緣讓出去。

二是重點靠段落開頭。讀者沿左緣往下跳時，掃到的是每段第一句。所以每段第一句要能單獨成立，是這段的結論句，不是引子。

落地做法：

- 每個 H2 底下第一句直接回答這節的問題。
- 每段第一句是斷言，不是鋪陳。「這款省電。」比「關於續航這個大家關心的問題，其實⋯」好。
- 條列項的第一個詞是關鍵詞，不是「可以」「建議」「其實」。

### 長方形排版的數字依據

手機直式閱讀，一行放太多字，眼睛橫向掃描的距離太長，容易跳行、讀丟。一行太少字又太碎。中文字方正，一行約 15 到 20 字時，視線幾乎不用左右大幅移動，靠垂直下滑就能讀完，整段看起來是一個窄長方形。

每段 2 到 3 行的來由：一個段落是一個意思單位。超過 3 行，一個段落塞了兩三個意思，讀者在同一塊視覺區裡要處理太多，負擔變重。2 到 3 行剛好裝一個完整的意思，段與段之間的空白讓眼睛有落腳點。

換算成字數，每段大約落在 80 到 150 字，絕不超過 200 字。這是排版經驗值，不是硬科學。

要留意的是這些數字是「約」。段落長度要長短交錯，不是每段都精準壓在 100 字。連續 3 段都同一個長度，視覺上變成整齊的磚牆，那本身就是一種機械感。

### 大腦省電模式

讀者的大腦預設走省電模式，能少花力氣理解就少花。這不是讀者懶，是所有人的預設。順著它寫，內容才進得去。

省電模式怕三樣東西：

- 長句。一句話塞三個子句，讀者要在腦中保持三段沒讀完的資訊，很耗。拆成短句。
- 抽象詞。「賦能」「生態」「範式」這種詞沒有具體畫面，大腦要額外翻譯。換成具體動作和東西。
- 名詞化。「進行了優化」比「調快了」耗力，因為它把動作包成一個名詞，讀者要拆開才懂。

順省電模式的三個動作：講一件事就一句、抽象換具體、名詞化改動詞。這三個貫穿後面每一節。

## 二、結構骨架五型：完整槽位表

骨架先搭，再填肉。下面每一型給出每個段落內部元素的順序、字數區間、一個範例大綱。字數是單段的參考區間，長短要交錯，不要每段都貼著上限寫。

### 通用開場三段

五型共用同一套開場。進正文前寫 2 到 3 段。

| 段 | 內部元素順序 | 字數區間 | 說明 |
|---|---|---|---|
| P1 鉤子加直答 | 破題句（20 字內）→ 直答句 → 一句補充 | 80 到 135 字 | 同段內必須出現能被獨立摘取的答案句 |
| P2 範圍界定 | 這篇處理什麼 → 不處理什麼 | 50 到 100 字 | 講清楚邊界，讀者知道值不值得讀下去 |
| P3 前置（選用） | 讀者要先知道的一個前提 | 50 到 90 字 | 只有真的需要前提才寫，不需要就跳過直接進正文 |

開場範例（解答型主題「筆電風扇一直轉怎麼辦」）：

> 風扇狂轉九成是某個程式在後台吃 CPU，先開工作管理員抓出它。（P1：破題加直答）
>
> 這篇只講 Windows 筆電、風扇突然變吵這一種狀況。硬體積灰、散熱膏老化那種要拆機的，這裡不談。（P2：範圍界定）

### 冷點收尾寫法

五型共用同一種收尾。停在冷靜的物理事實，或還沒解決的問題。不拔高、不總結、不掛金句。

冷點收尾三種可用開法：

- 停在一個具體動作或畫面：「重開機之後風扇轉了大概十秒就安靜了。」
- 停在一個還沒解的問題：「我還沒搞懂為什麼只有插電時會這樣，改天再測。」
- 停在一個限制：「這個方法只在這台機器上試過，別的型號不保證。」

收尾禁區：「希望這篇對你有幫助」「說到底，工具是死的人是活的」「未來可期」「這讓我想起⋯」。這些都是升華，一律不寫。

### 骨架一：解答型（資訊型 query）

| 段位 | 內部元素順序 | 字數區間 |
|---|---|---|
| 直答 | 一句話結論 → 一句話為什麼是這個結論 | 60 到 110 字 |
| 為什麼 | 機制或原因 → 一個具體例子 | 90 到 150 字 |
| 怎麼做 | 步驟或做法（能編號就編號） | 每步 40 到 80 字 |
| 限制條件 | 這個答案何時不成立 → 誰不適用 | 70 到 120 字 |

範例大綱（主題「早上喝咖啡到底該不該空腹」）：

1. 直答：多數人空腹喝沒問題，除非你本來就胃食道逆流。
2. 為什麼：空腹和咖啡刺激胃酸的關係，實際上因人差很多。
3. 怎麼做：想避開就配一口食物，或延到早餐後半小時。
4. 限制條件：有胃潰瘍、逆流、正在吃特定藥的人另當別論。

### 骨架二：工具型（docs、教學）

| 段位 | 內部元素順序 | 字數區間 |
|---|---|---|
| 前置 | 開始前要備好什麼 → 版本或環境 | 60 到 110 字 |
| 編號步驟 | 動作 → 預期看到的結果 | 每步 30 到 70 字 |
| 常見狀況排除 | 症狀 → 原因 → 解法 | 每條 40 到 90 字 |
| 實測紀錄 | 我實際跑的結果（沒素材就整段省略） | 60 到 120 字 |

範例大綱（主題「把網站部署到 Cloudflare Pages」）：

1. 前置：要有 GitHub 帳號、一個能 build 的專案、Node 版本確認。
2. 步驟：連 repo、設 build 指令、設輸出資料夾、按部署，各步附「這時畫面會出現什麼」。
3. 常見狀況：build 失敗多半是輸出資料夾填錯、環境變數沒設。
4. 實測紀錄：這次部署從連 repo 到上線花了幾分鐘（有實測才寫，沒有標 `[待補]`）。

工具型注意：術語不改、不硬塞口語、不塞幽默。步驟一定編號。

### 骨架三：比較型（商業調查 query）

| 段位 | 內部元素順序 | 字數區間 |
|---|---|---|
| 評估標準 | 我用哪幾個標準比 → 為什麼是這幾個 | 90 到 150 字 |
| A 情境 | A 的優點 → A 的缺點 → A 適合誰 | 100 到 160 字 |
| B 情境 | B 的優點 → B 的缺點 → B 適合誰 | 100 到 160 字 |
| 對照表 | 逐項並排 | 表格 |
| 誰不適合 | 兩個都別選的情況 | 60 到 110 字 |

範例大綱（主題「Notion 還是 Obsidian」）：

1. 評估標準：離線、同步、學習曲線、費用，四項。
2. A 情境 Notion：協作強、上手快、離線弱、資料在別人伺服器。
3. B 情境 Obsidian：本地檔案、離線強、要自己搞同步、學習曲線陡。
4. 對照表：四個標準逐列打勾。
5. 誰不適合：只想馬上開始寫、不想折騰的人兩個都會嫌。

比較型注意：兩邊都要寫缺點，不能一面倒。缺點寫具體，不是「可能不太適合某些人」。

### 骨架四：敘事型（日誌、觀點）

| 段位 | 內部元素順序 | 字數區間 |
|---|---|---|
| 場景事實 | 時間地點 → 發生了什麼具體的事 | 80 到 140 字 |
| 展開轉折 | 本來以為 → 結果不是 | 100 到 160 字 |
| 冷點收尾 | 停在事實或未解問題 | 50 到 100 字 |

範例大綱（主題「換了機械鍵盤三個月的感想」）：

1. 場景事實：三個月前買了某軸鍵盤，第一週的具體手感。
2. 展開轉折：本來以為打字會變快，結果快的不是速度是別的。
3. 冷點收尾：停在一個具體觀察，不總結「工具改變生活」。

敘事型注意：轉折要真的有轉折，不是為了公式硬安一個。冷點收尾最容易滑進升華，寫完盯著最後一句檢查。

### 骨架五：說服型（landing）

| 段位 | 內部元素順序 | 字數區間 |
|---|---|---|
| 痛點 | 讀者現在卡在哪 → 具體場景 | 80 到 140 字 |
| 賣點具體化 | 賣點 → 換算成讀者能感受的具體結果 | 每點 60 到 110 字 |
| 證據 | 數據或案例（要來源，無來源標 `[待補]`） | 80 到 130 字 |
| 反對意見處理 | 讀者會有的疑慮 → 正面回應 | 70 到 120 字 |
| CTA | 一個明確動作 | 30 到 60 字 |

範例大綱（主題「一款自動記帳 App 的落地頁」）：

1. 痛點：月底想看錢花哪去，翻半天帳單湊不齊。
2. 賣點具體化：綁定後自動歸類。別寫「智能記帳」，改寫「打開就看到這個月外食花了多少」。
3. 證據：留存或準確率數據，有實測填實測，沒有標 `[待補]`，不編。
4. 反對意見：擔心銀行資料安全，正面講加密和權限。
5. CTA：一個動作，例如「先綁一張卡試一個月」。

說服型注意：landing 保留必要重複，不為多樣化砍賣點。證據數字是最容易造假的地方，沒來源一律 `[待補]`。

## 三、具體化對照庫（400 萬單位感官捕捉）

抽象形容詞不給大腦畫面，具體參數給。下面分三類收 before/after。抓不到具體時，問自己：這件事如果拍成照片或影片，鏡頭裡會出現什麼。只換同義詞不算具體化（「重要」改「關鍵」不算）。

### 感官類（視、聽、觸、嗅）

| 抽象 | 改成具體 | 走的感官 |
|---|---|---|
| 很擠 | 尖峰七點半的板南線，門一開只能側身塞進去 | 視 |
| 房間很亂 | 桌上三個沒洗的馬克杯，鍵盤縫卡著餅乾屑 | 視 |
| 光線很美 | 下午四點的光斜進來，牆上一條一條的百葉窗影 | 視 |
| 很吵 | 隔壁工地的電鑽聲，隔著兩層牆還在耳朵裡震 | 聽 |
| 很安靜 | 安靜到聽得見冰箱壓縮機啟動的那聲低鳴 | 聽 |
| 超香 | 一進門就是現磨曼特寧那股焦糖味 | 嗅 |
| 味道很怪 | 開冰箱那瞬間，一股放太久的蔥味沖出來 | 嗅 |
| 手感很好 | 按下去的那一下，指腹先陷一段再頂到底 | 觸 |
| 很燙 | 杯壁隔著紙套還是要一直換手拿 | 觸 |
| 很冷 | 手指按快門按到僵，得先呵口氣才彎得動 | 觸 |

### 參數類（數值、品牌、型號）

| 抽象 | 改成具體 |
|---|---|
| 這個工具很強大 | 匯入 10GB 檔案，3 秒內搜到第 14 個檔 |
| 電池很耐用 | 早上八點滿電出門，晚上十點還剩三成 |
| 檔案很大 | 一支影片就 4.2GB，隨身碟一插就滿 |
| 反應很快 | 按下快門到存檔，中間幾乎沒有等 |
| 很省 | 一個月電費從九百多掉到六百出頭 |
| 螢幕很好 | 大太陽底下也看得清，亮度拉滿不反白 |
| 很輕 | 塞進側背包，走一整天肩膀不酸 |
| 很多人用 | 我認識的設計圈朋友幾乎都在用（`[本人]` 觀察，非統計） |

參數類注意：凡是寫進數字的地方要對得起素材級別。素材裡有的數字照抄，素材外的精確數字不編，該標 `[待補]` 就標。上表「九百多掉到六百」這種要有本人帳單撐，沒有就寫成質性描述。

### 動作類（把狀態改成看得到的動作）

| 抽象狀態 | 改成具體動作 |
|---|---|
| 好累 | 眼皮撐到早上四點，第三次泡咖啡 |
| 很緊張 | 手心的汗把手機背面都沾濕了 |
| 很猶豫 | 購物車放了三天，每天打開看一次又關掉 |
| 很專心 | 泡的茶涼了都沒發現，回神已經兩小時 |
| 賦能 / 打造 | （拆成實際動作流程，不用這兩個詞） |
| 至關重要 | 這步漏了，後面整批資料要重跑 |
| 提升效率 | 本來手動貼三十次，現在跑一次腳本就好 |
| 優化了流程 | 把兩個表單併成一個，少填一次資料 |

動作類是最有效的一類。狀態形容詞（累、急、猶豫）幾乎都能翻成一個具體動作，翻完讀者自己感覺得到那個狀態，不用你講。

每篇至少 3 處具體化，感官、參數、動作三類都碰到最好。

## 四、系統 1 白話

系統 1 是大腦不用刻意思考就懂的那一層。白話就是寫到讀者用系統 1 就接住，不用停下來翻譯。

### 名詞化改動詞化

名詞化是把一個動作包成名詞，例如「做了一次調查」裡真正的動作是「調查」，卻被「做了一次」包成名詞片語。拆開改回動詞，句子就活。

| 名詞化 | 改動詞化 |
|---|---|
| 進行了一次調查 | 我測了 5 個 |
| 對系統做了優化 | 把系統調快了 |
| 進行問題的排查 | 一個一個找出哪裡壞了 |
| 做出了決定 | 決定了 |
| 給予支持 | 支持 |
| 完成了對資料的整理 | 把資料整理好了 |
| 實現了效率的提升 | 變快了 |
| 針對此事展開討論 | 討論了這件事 |

判斷法：看到「進行」「做出」「給予」「實現」「展開」加一個名詞，八成是名詞化，把那個名詞還原成動詞。

### 轉折詞刪除判斷樹

轉折詞（但、然而、其實、不過）用對是邏輯關節，用成口頭禪就是雜訊。每個轉折詞問一次這棵樹。

```
看到一個「但 / 然而 / 其實 / 不過」
│
├─ 前後兩句是不是真的相反 / 相衝突？
│   ├─ 是 → 這個轉折是邏輯需要，留。
│   └─ 否 → 往下問。
│
├─ 拿掉它，兩句話還讀得通嗎？
│   ├─ 讀得通 → 口頭禪，刪。
│   └─ 讀不通（少了它語氣斷掉） → 往下問。
│
└─ 是不是拿它當段落 / 句子的開場暖身？
    ├─ 是（「其實⋯」「說到底⋯」開頭）→ 口頭禪，刪，直接講內容。
    └─ 否，且確實有輕微語氣轉折 → 可留一個，但同一段別出現第二個。
```

範例：

- 「這款很輕，其實我出門都帶著。」→ 前後不相反，「其實」是口頭禪，刪：「這款很輕，我出門都帶著。」
- 「這款很輕，但續航只有四小時。」→ 輕和續航短是真的相衝突，「但」留。

「其實」「說到底」「真正的」當開頭是最常見的口頭禪，看到先假設要刪。

### 白話註解密度規則

專有名詞、英文詞、術語第一次出現用括號白話註解一次。規則如下，違反就是白話化長出來的新 AI 味。

- 首次出現：註解。例「CDN（把檔案放到離使用者近的伺服器，載入比較快）」。
- 後續出現：直接用該詞，不再註解。同一篇裡「CDN」第二次、第三次出現都不加括號。
- FAQ 或獨立成段可再註解一次：如果有 FAQ 區塊，讀者可能跳著讀，該詞在 FAQ 裡第一次出現可以再註解一次，因為那段可能脫離上文被單獨讀。

重複括號註解（同一個詞每次出現都掛白話解釋）是要抓的錯，不是勤勞。

### 白話深度預設

預設向 5 歲看齊。意思是預設讀者不懂任何術語，每個專業詞都當第一次聽到處理。這是安全預設，寫給大眾一定夠白。

技術或專業讀者放寬：目標讀者是工程師、醫師、同行時，共通術語不用註解（對工程師不用解釋「API 是什麼」），但仍不寫學術腔，仍優先動詞加具體名詞。放寬的是術語註解密度，不是把句子寫複雜的許可。

判斷靠 §0 輸入合約的「目標讀者」欄。那一欄決定這一節鬆到哪。

## 五、鉤子公式庫

第一句 20 字以內破題，同段內必出現直答句。下面 6 種開法，各配中文範例。挑一種，不要疊。

### 一、痛點直戳

點破讀者現在正卡的那件事。

- 「手機一天要充兩次電，出門就焦慮。」
- 「試算表拉到第三十列就開始卡。」

### 二、現象陳述

丟一個讀者也觀察到、但沒細想的現象。

- 「最近每家咖啡廳都在賣生椰拿鐵。」
- 「line 群組已讀不回的人越來越多。」

### 三、反常識

先講一個和多數人直覺相反的結論。

- 「早睡不一定讓你比較不累。」
- 「加更多鏡頭，拍出來不一定更清楚。」

### 四、具體場景

直接把讀者丟進一個他認得的畫面。

- 「凌晨兩點，你第五次點開同一個購物車。」
- 「開會開到一半，投影幕突然黑掉。」

### 五、具體數字開場

用一個沒頭沒尾的數字勾住好奇。

- 「三個月，我刪掉了四十個沒在用的 App。」
- 「五百塊的耳機，我用得比三千塊那副還久。」

（數字要真，來自本人素材或可查來源，不編。）

### 六、一句話結論前置

把整篇的答案濃縮成一句直接砸出來。

- 「風扇狂轉，先抓後台吃 CPU 的程式。」
- 「想早起，關鍵不在鬧鐘在前一晚。」

六種挑一種當第一句，接著同段補直答句和一句延伸。禁開場套話：「在當今⋯時代」「隨著⋯快速發展」「讓我們一起來看看」「本文將深入探討」「如何⋯已成為重要議題」。

## 六、幽默公式：理性堆疊四步

只在場景與語域容許、素材撐得起時用。荒謬來自語氣和內容的反差，不是加感嘆號或塞網路梗。四步如下。

1. 具體小觀察：先給一個真實、細小、不誇張的觀察。
2. 冷靜拆解：用一本正經的口氣分析它，好像在講很嚴肅的事。
3. 荒謬演算法：把這個分析推到一個一絲不苟但明顯過頭的結論。
4. 不予置評：講完就停，不解釋、不吐槽自己好笑，讓反差自己發酵。

範例一：

> 我家的貓每天早上六點準時踩我臉。（觀察）不是六點零五，不是五點五十五，是六點整。（拆解）我開始懷疑牠體內有一顆比我手機還準的石英振盪器，誤差不超過三十秒，且不受夏令時間影響。（荒謬演算法）目前還在觀察牠會不會自己校時。（不予置評）

範例二：

> 這台印表機只有在我趕時間的時候卡紙。（觀察）我做了紀錄，不趕時間的時候它一次都沒卡過。（拆解）合理推論是它能偵測我的心率，並在偵測到焦慮峰值時啟動卡紙程序，藉此維持某種微妙的權力平衡。（荒謬演算法）我還沒找到它的感測器裝在哪。（不予置評）

範例三（收得更短）：

> 早餐店阿姨記得我不加糖，卻永遠記不得我的臉。（觀察加拆解）我推測她的大腦把客人索引在飲料偏好上，而不是長相，這是一套為出餐速度最佳化的資料結構。（荒謬演算法）我尊重這個設計。（不予置評）

什麼時候不用：

- docs、公文、API 文檔：不用。
- 嚴肅主題（醫療、災難、財務損失、他人不幸）：不用。
- 素材撐不起，只能靠感嘆號和「笑死」硬撐：不用，寧可平鋪。
- 不確定該不該用：不用。幽默是加分項，不是必需品，失手比不用傷更大。

## 七、句長變異的中文節奏參考

英文有兩個現成指標：perplexity（用詞可預測度）和 burstiness（句長起伏度）。AI 生成的英文常常兩個都偏低，句子一樣長、用詞一路平順。這兩個概念方向對，但不直接套中文。中文按自己的節奏判準看三樣東西。

### 一、詞重複率

看同一個詞在鄰近句子裡是不是重複太密。這裡分兩種重複，方向相反。

- 該重複的關鍵詞：實體全名、核心術語，要重複，不要用同義詞輪轉。「開發者、工程師、實踐者、建構者」繞圈是 AI 味，該叫「開發者」就一路叫「開發者」。
- 不該重複的填充詞：「這個」「其實」「所謂」「一種」這類詞在一段裡出現三四次就是雜訊，刪到剩必要的。

判斷法：關鍵詞重複是好的，填充詞和連接詞重複是要清的。

### 二、句型重複率

看連續幾句是不是同一個句型模子印出來的。AI 生成中文最明顯的節奏病是句型單一。

要抓的重複句型：

- 連續句都是「主語 + 是 + 一個 + 形容詞 + 的 + 名詞」。
- 連續句都用「透過⋯來⋯」「藉由⋯達成⋯」。
- 連續句都是相同長度、相同結構的排比（除非內容真的是三項並列）。

破法：一段裡混句型。一個短斷言，接一個帶條件的長句，再接一個問句或一個具體畫面。長短句型交錯，節奏就起來了。

### 三、轉折詞頻率

數一段裡「但、然而、其實、不過、所以、因此」總共幾個。密度過高，讀起來像每句都在跟前句掰手腕，很累。用第四節的刪除判斷樹逐個過，留真的有邏輯關節的，刪當口頭禪的。

### 中文自己的節奏判準

不套 perplexity、burstiness 的數值，改看這三個可直接觀察的信號：

| 信號 | 平（AI 味重）長怎樣 | 有節奏長怎樣 |
|---|---|---|
| 句長 | 連續句子都 15 到 20 字，均勻 | 短句（10 字內）和長句（25 字以上）混在一段 |
| 句型 | 連續句同一個模子 | 斷言、帶條件長句、問句、畫面交錯 |
| 段長 | 連續 3 段同一字數區間 | 段落長短交錯，磚牆感消失 |

自檢時朗讀一段。念起來每一口氣都一樣長、一樣平，就是節奏死了。念起來有停、有衝、有喘口氣的地方，節奏就對了。中文的節奏靠讀出來判，不靠算分數。

## 八、補充：白話化到失真的護欄

改寫時的保真回讀有一條問句：「有沒有把技術術語口語化到失真」。前面第四節整節在推白話化，卻沒有一條反向護欄提醒「白話化過頭會把術語講錯」，這裡補上。這是生成當下就能避開的失誤，不是事後改寫才處理。

### 白話化到失真：把白話化踩煞車的那條線

第四節要求把術語翻成白話，這是對的方向。但白話化有一個上限：不能為了好懂，把術語的意思講到偏掉。好懂和正確衝突時，正確優先。

判斷法很簡單，白話註解寫完後回讀一次，問這句白話換掉原術語後，句子的意思有沒有變。沒變才算合格的白話化，變了就是失真，要收回來。

| 術語 | 失真的白話化（好懂但講錯） | 合格的白話化（好懂又不偏） |
|---|---|---|
| API | 讓兩個軟體聊天的東西 | 一組固定的呼叫規格，A 程式照這個規格就能叫 B 程式做事 |
| 快取（cache） | 把東西記起來 | 把常用資料先存在近處，下次不用重算或重抓 |
| 加密 | 把資料鎖起來別人看不到 | 把資料轉成沒鑰匙就讀不懂的形式，有鑰匙的人才還原得回去 |
| 遞迴 | 一直重複做 | 一個function在自己內部再叫自己一次，直到滿足停止條件 |

左欄不是不能講得更淺，是它把界線講掉了：「記起來」漏了「近處、下次省時」這個快取的重點，「一直重複」把遞迴和迴圈混成同一件事。白話化的技術是「換更好懂的講法」，不是「換更模糊的講法」。

### 給技術與專業讀者時，這條煞車更緊

第四節說技術讀者可以放寬術語註解密度。放寬的是「要不要加括號解釋」，不是「可以把術語講得不精確」。對工程師寫「API」不用註解，但只要你動手註解，那個註解就要對得起原意，不能為了顯得親切而失真。

一句話收束：白話是為了讓對的資訊更快進到讀者腦裡，不是讓資訊在變白話的路上悄悄變錯。查不準原術語的精確意思時，寧可少解釋一句，也不要生一個好懂但錯的白話版；真的沒把握就標 `[待查]`，比照 SKILL §5 誠實邊界處理。
